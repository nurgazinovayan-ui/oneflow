# Аудит безопасности ONEFLOW — октябрь 2026

Проверялись два репозитория: `oneflow` (веб-приложение, Supabase Edge Functions, миграции) и `test_ayan/admin` (админка `oneflow.art/admin`, функция `admin-api`). Проверка шла по исходному коду, плюс тесты на локальном PostgreSQL 16 и Deno 2 с подменёнными Supabase и AI-провайдерами. Production-инфраструктура (Supabase Dashboard, Vercel, DNS, бэкапы) не проверялась: доступа к ней нет. Что из этого нужно проверить вручную, перечислено в разделе 5.

Статусы:
- **реализовано** — код изменён и закоммичен;
- **проверено** — изменение покрыто тестом, тест проходит;
- **подготовлено** — механизм готов, но включается вашей настройкой;
- **не выполнено** — требует доступа или решения владельца.

### Путь генерации (после исправлений)

1. Клиент отправляет `POST /functions/v1/generate-*` с JWT и заголовком `Idempotency-Key`, уникальным для каждого вызова.
2. Edge Function:
   - проверяет JWT через `auth.getUser`;
   - ограничивает размер тела (48 МБ);
   - проверяет модель и параметры по своей серверной таблице цен;
   - сама считает стоимость. Сумма, баланс и `user_id` из тела запроса игнорируются.
3. Функция вызывает `reserve_generation_v2`. Это одна транзакция под advisory-lock пользователя, в ней по порядку проверяются:
   1. выключатель (`paid_generation_enabled`);
   2. блокировка аккаунта (`generation_blocks`);
   3. подтверждение email;
   4. потолок стоимости одной задачи;
   5. ключ идемпотентности;
   6. частота запросов от аккаунта и от IP;
   7. число параллельных задач;
   8. глобальный дневной и часовой лимит;
   9. дневной лимит аккаунта;
   10. пул организации;
   11. кредиты (за вычетом долга) или месячный лимит для override-аккаунтов.

   Если всё в порядке, создаётся строка-резерв. Если шлюз недоступен, функция отвечает 503 (fail closed): без резерва платного вызова не бывает.
4. Вызов провайдера, с таймаутом.
5. Синхронные модели: `settle_generation` один раз списывает реальную стоимость из `usage.cost`, пишет `generation_log` и `credit_ledger`. Если стоимость больше остатка, разница записывается в `credit_debts`. При ошибке провайдера вызывается `release_generation`.
6. Видео:
   1. Провайдер принял задачу → `mark_generation_submitted`. С этого момента резерв не снимается автоматически.
   2. Функция ждёт до 100 секунд. Если видео не готово, ответ 202 `{pending, jobId}`.
   3. Клиент опрашивает `{jobId}`. Задача видна только владельцу.
   4. Ровно один опрос получает право завершить задачу (`claim_generation_completion`): скачивает видео, сохраняет его и списывает кредиты.
   5. Задачу, которую никто не опросил за 24 часа, `reconcile_generations` списывает по оценке, потому что провайдер её уже выставил к оплате.
7. Зависшая синхронная задача (функция упала) через 20 минут получает статус `expired`. Бюджет освобождается, событие пишется в журнал.

## 3. Проверено без изменений

- **Доступ к данным пользователей.**
  - `generation_log`, `subscriptions`, `admin_messages` закрыты RLS «только свои строки».
  - Таблицы денег, журналов и настроек недоступны ролям `anon` и `authenticated`.
  - Пользователь B не видит строки A. Тест §14.
- **Мессенджер.** Чтение, отправка, отметка прочтения и загрузка файлов проверяют членство в чате по email из проверенного JWT. «Коллеги» требуют подтверждённого email.
- **Яндекс.Диск.** Токен ищется по `user_id` из JWT. Токены зашифрованы AES-GCM.
- **Админка.**
  - Каждое действие проверяет администратора на сервере.
  - Вводы проходят очистку, ссылки допускаются только `https:` или `mode:`.
  - Медиа принимаются только из своего бакета, по шаблону пути.
- **XSS.**
  - В приложении нет `dangerouslySetInnerHTML`; markdown модели выводится текстовыми узлами.
  - На лендинге нет `innerHTML`, тексты из CMS вставляются через `textContent`.
- **Сессии и OAuth.**
  - Сессия хранится в памяти и `sessionStorage`, без cookie, поэтому CSRF к API неприменим.
  - Токен OAuth сразу удаляется из URL.
  - Electron: `contextIsolation: true`, `nodeIntegration: false`.
- **SQL injection.** Запросы идут через PostgREST и параметризованные функции. В `search_trends` ввод экранируется.

## 5. Не удалось проверить с текущим доступом

- Supabase Dashboard: настройки Auth, MFA, «Verify JWT» у каждой функции, секреты, сетевые ограничения БД, PITR и бэкапы.
- Vercel: Firewall/WAF, Attack Challenge Mode, дополнительные домены (`*.vercel.app`), логи.
- DNS и поддомены `oneflow.art`, открытые порты. Своего origin-сервера нет, весь трафик идёт в Vercel и Supabase.
- Реальные лимиты OpenRouter (credit limit ключа) и счета провайдеров.

Проверка нагрузки в production не проводилась. Распределённый лимитер проверен только на локальной БД: 20 параллельных сессий при лимите 5 пропустили ровно 5.

## 6. Тесты и как их повторить

Все тесты локальные: одноразовая база и подменённые Supabase и провайдеры. Ни одного запроса в production, ни одной платной генерации.

| Набор | Команда | Результат на момент коммита |
|---|---|---|
| База: права, кредиты, долги, лимиты, выключатель, блокировка аккаунта, вебхук, асинхронные задачи | `PGHOST=… PGPORT=… PGUSER=postgres bash tests/security/run_db_tests.sh` | 42 проверки, `ALL DB SECURITY TESTS PASSED` |
| Параллельность: 25 резервов на 50 кредитов, 10 запросов с одним ключом, 5 параллельных списаний, лимитер на 20 сессий | входит в `run_db_tests.sh` (`concurrency_test.sh`) | ровно 10 / 1 / 1 / 5, `CONCURRENCY TESTS PASSED` |
| Повторный запуск миграции | миграция дважды на одной базе | без ошибок; пороги владельца и блокировки сохраняются |
| Edge Functions: настоящие файлы функций, подменённый `fetch`; любой неожиданный внешний запрос — ошибка теста | `DENO=… bash tests/security/run_edge_tests.sh` | 105 проверок в 14 наборах, `EDGE SECURITY TESTS PASSED` |

| Браузер: веб-клиент проходит асинхронное видео (202 → опрос `{jobId}` → результат), шлёт `Idempotency-Key` только в первом запросе | Playwright со всеми запросами к Supabase, подменёнными локально | пройдено, ошибок JS нет |
| Регрессия интерфейса: лендинг, приложение, админка, окна согласия | Playwright | 0 ошибок JS |
